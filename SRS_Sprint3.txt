Documento de Especificación de Requerimientos del Sistema (SRS) MVP 3Proyecto: App Móvil de Gestión de Voluntariado UNITYFase: Tercer MVP (Sprint 3)Duración del Sprint: 1 Semana1. Arquitectura y Restricciones Generales• Stack: Python, Flet (UI móvil local), Supabase (PostgreSQL para persistencia y Auth).• Patrón de Diseño: Separación Estricta de Responsabilidades (SoC). Las vistas en el directorio views/ solo consumen y muestran datos. La lógica reside exclusivamente en core/.• Integración de Datos: Se mantendrá la infraestructura del MVP 2 utilizando supabase_client.py y data_repository.py. Todo desarrollo se realizará directamente sobre el esquema existente en la nube, garantizando la conservación del historial de usuarios, inventario y emergencias previas.• Diseño Atómico: Se exigirá el uso de variables semánticas desde design_tokens.py para asegurar la coherencia visual.2. Especificación de Historias de Usuario2.1. S3_HU01: Calendario de Gestión de Turnos• Lógica de Negocio: Consultar la disponibilidad de usuarios de una cuadrilla específica en Supabase y mapearla en una matriz de tiempo. El usuario con rol "Líder de Cuadrilla" es el único con permisos de escritura. Los voluntarios tienen acceso de solo lectura. Antes de la inserción en la base de datos de Supabase, el algoritmo debe validar solapamientos: si el usuario_id ya posee un bloque que colisione con el nuevo intervalo, se cancela la operación de red y se muestra un SnackBar ("Bloque horario ya asignado").• Interfaz de Usuario (UI): Renderizar una cuadrícula semanal utilizando contenedores de Flet. Aplicar la regla de componentización recursiva si los bloques superan las 20 líneas de código. Estados visuales: Turno Libre, Turno Asignado, Conflicto.• Capa de Datos: Nueva tabla turnos con llaves foráneas a perfiles y cuadrillas.• Criterio de aceptación: Ante una colisión de turnos al guardar, la capa de datos validará la disponibilidad del bloque antes de ejecutar la inserción en Supabase. Si el intervalo ya fue ocupado, se cancela la operación y la interfaz despliega un SnackBar con el mensaje "Bloque horario ya asignado".• Manejo de Red: S3_HU01 (Calendario): Si la transacción de red hacia Supabase falla al intentar guardar o modificar un turno, la operación se aborta de inmediato y la interfaz despliega un SnackBar básico con el texto "Error de red. No se pudo guardar el turno." para evitar bucles de carga infinitos.• Lógica de Solapamiento: Basado en el esquema de base de datos donde existe perfiles.cuadrilla_id, se confirma que un usuario pertenece a una única cuadrilla. El algoritmo de ordenamiento y solapamiento se reduce a una validación condicional al momento de guardar: el sistema rechazará la creación de un registro en la tabla turnos si el usuario_id ya posee una asignación cuyo intervalo (inicio_hora y fin_hora) colisione con el nuevo bloque ingresado.2.2. S3_HU02: Chat Interno de Coordinación por Cuadrilla• Lógica de Negocio: Filtrar el flujo de mensajes estrictamente por el cuadrilla_id del perfil del usuario autenticado. Implementar un mecanismo de actualización mediante polling asíncrono local cada 3 segundos, consultando únicamente los nuevos registros basados en el timestamp del último mensaje recibido. Se descarta Supabase Realtime para este MVP para evitar la complejidad de manejo de caídas de conexión WebSocket y optimizar el consumo de tokens durante el desarrollo. Si el usuario tiene un cuadrilla_id nulo, aplicar un patrón Early Return en la inicialización, deshabilitar campos de texto y mostrar estado vacío.• Interfaz de Usuario (UI): Vista de lista desplazable (ListView) con burbujas de chat. Aplicar resiliencia visual manejando el estado de vaciado para chats sin historial y desbordamiento de datos para mensajes muy extensos.• Capa de Datos: Nueva tabla mensajes_chat con vinculación al usuario_id emisor y la cuadrilla_id receptora.• Frecuencia de Polling: El polling se ejecutará cada 3 segundos utilizando tareas asíncronas en Flet, consultando Supabase. Este intervalo garantiza la inmediatez crítica para la coordinación de emergencias y evita la saturación del hilo principal de la interfaz o el consumo excesivo de llamadas de red hacia el backend.• Criterio de Aceptación: Si el usuario autenticado tiene un cuadrilla_id nulo o inválido, la vista aplicará un patrón Early Return en su inicialización. Renderizará un componente de estado vacío ("No tienes una cuadrilla asignada") y mantendrá deshabilitado el campo de texto y el botón de envío.• Manejo de Error: Si el polling de 3 segundos falla por pérdida de conectividad, la aplicación descarta silenciosamente ese ciclo de actualización y reintenta en el siguiente. Si la falla persiste por más de 3 ciclos consecutivos (9 segundos), se muestra un aviso sutil en la parte superior del chat indicando "Buscando conexión...", el cual desaparece automáticamente cuando la red se restablece.2.3. S3_HU03: Reporte Preciso de Emergencias con Pin Editable• Lógica de Negocio: Capturar coordenadas X e Y relativas de un clic sobre la imagen estática de la zona afectada y aplicar interpolación lineal para transformarlas en latitud y longitud.• Interfaz de Usuario (UI): Dropdown con categorías estandarizadas de emergencia. Visualizador de mapa simulado con un icono de pin desplazable.• Capa de Datos: Adición de la columna tipo_emergencia a la tabla existente alertas_sos.• Asset de Mapa y Sistema de Coordenadas: El asset visual será una imagen estática de referencia de la zona afectada que se deberá incorporar a los recursos del proyecto durante este sprint. La base de datos mantendrá los campos latitud y longitud. Para realizar la conversión, la lógica de negocio incluirá una función de interpolación lineal que transformará las coordenadas X e Y relativas del clic en la pantalla hacia una caja delimitadora (bounding box) de coordenadas geográficas reales predefinidas.• Criterio de Aceptación: Validar los datos de entrada aplicando un patrón Early Return si existe ausencia de coordenadas o tipo de emergencia. Si la transacción hacia Supabase falla por problemas de red, se aborta el proceso y se muestra un banner de error solicitando al usuario que reintente el envío.2.4. S3_HU04: Alerta SOS con Notificación a Cuadrilla• Lógica de Negocio: Al registrar exitosamente una alerta en alertas_sos (con resuelta = False por defecto), la capa de negocio inyectará simultáneamente un registro destacado en la tabla mensajes_chat de la cuadrilla del usuario.• Interfaz de Usuario (UI): Botón flotante persistente con color de nivel danger. La notificación aprovechará la interfaz de la HU02 para renderizar un componente de mensaje de alerta diferenciado.• Capa de Datos: Operación de inserción dual sobre alertas_sos y mensajes_chat.• Criterio de Aceptación: Si la inserción dual falla en este punto específico (pérdida de conectividad entre la creación del SOS y la inyección del chat o inconsistencias relacionales), el sistema capturará la excepción y mostrará un banner de error advirtiendo que la alerta central fue procesada pero la notificación interna a la cuadrilla no pudo sincronizarse.3. Modelo de Datos (Supabase / PostgreSQL)• perfiles (existente): id (uuid), nombre_completo, rol, cuadrilla_id (uuid, nueva columna)• cuadrillas (nueva): id (uuid), nombre_cuadrilla (text)• turnos (nueva): id (uuid), usuario_id (uuid), inicio_hora (timestamptz), fin_hora (timestamptz), dia_semana (int)• mensajes_chat (nueva): id (uuid), cuadrilla_id (uuid), usuario_id (uuid), texto_mensaje (text), es_alerta (bool), timestamp (timestamptz)• alertas_sos (modificada): id, usuario_id, latitud, longitud, resuelta, fecha_alerta, tipo_emergencia (text, nueva columna)4. Reglas de Negocio Específicas y Parámetros del Sistema4.1. Autenticación y Manejo de Sesión: El sistema continuará utilizando la lógica de sesión del MVP 2. Al iniciar la aplicación, los identificadores user_id, rol y el nuevo cuadrilla_id se mantendrán en el estado global (como state["user_id"] o page.session). Todas las validaciones de permisos de escritura (Calendario) o filtros de lectura (Chat) consumirán estas variables alojadas en memoria, manteniendo sincronía directa con los datos persistidos en Supabase.4.2. Gestión del campo "resuelta" en Alertas SOS: El campo "resuelta" se definió en el modelo de datos como base estructural para un futuro sprint donde se integrará un panel de administración para el Comando Central. Para el alcance estricto de este MVP3, toda alerta generada se insertará con el valor resuelta = False por defecto. Ningún usuario tendrá la opción en la interfaz para modificar este estado, acotando el flujo exclusivamente a la emisión de la emergencia y la notificación a la cuadrilla.4.3. Migración de datos al nuevo esquema (MVP2 a MVP3)• Estado inicial de los datos: La nueva columna cuadrilla_id en la tabla perfiles se creará aceptando valores nulos (NULL). Todos los usuarios históricos provenientes del MVP2 iniciarán este sprint con dicho campo en NULL.• Impacto en el flujo y resolución: Es completamente viable mantener este estado inicial. Al iniciar la aplicación, los usuarios con cuadrilla_id = NULL verán el estado vacío del chat especificado en la HU02 ("No tienes una cuadrilla asignada"). Esto no altera la base de datos ni corrompe el sistema. El bloqueo del Early Return se resolverá de manera operativa cuando un usuario con rol de Comando o Líder de Cuadrilla edite el perfil del voluntario y le asigne una cuadrilla formal, actualizando el campo en Supabase y habilitando el acceso al chat en el siguiente inicio de sesión o recarga.
